# Fix plan: floating widgets (both platforms), masked settings, two-finger right-click

## Issues & root causes

1. **Phone Clipboard shows "Set your key in More → Remote to sync" / composer does nothing**
   `clipboardCompanion.ts:init()` reads the secret from `localStorage["gt.remote.secret"]`. The secret only gets written there from `Pairing.tsx` (typed into the *optional* permanent-key box). If the user paired *without* entering a permanent key, the Clipboard tab has no key → `ready=false` → nothing syncs, nothing sends. The "key" is the PC's `remote_secret_code` (shown on the desktop Remote page), not anything the companion already has.
2. **Android floating bubble opens the full app instead of working standalone**
   `ClipboardService.java::DragTap.openApp()` always launches the launch intent with `gt_open=clipboard`. The bubble has no UI of its own.
3. **Desktop floating widget not visible**
   `index.html` sets `#root { background: #06070d }`, and `src-tauri/tauri.conf.json` has the main window `transparent: false`. The overlay window is created with `transparent(true)` but the same `index.html` paints an opaque `#06070d` root rectangle, hiding the transparent bubble behind a solid dark square. (`ClipboardOverlay.tsx` only clears `documentElement/body` background — never `#root`.)
4. **Settings → Shared clipboard panel "masked off"**
   `ClipboardSettings.tsx` renders `<ClipboardIntro>` as a sibling *inside* the Settings `<Panel>` (which is `relative overflow-hidden` inside a Framer `motion.div`). The modal is `position: fixed`, but a CSS transformed+clipped ancestor becomes its containing block, so it's trapped inside the short panel viewport — the bottom buttons get cut off.
5. **Two-finger tap → right-click unreliable**
   In `Control.tsx::onPointerUp`, the right-click check is `now - downT.current < TAP_MS`. `downT` is set at the **first** pointer-down (single finger) and never updated when the second finger lands. A two-finger tap that takes longer than 260ms total (very common — two fingers rarely land within 50ms of each other) silently fails the tap test. Also `wasTap` reads `maxMove` accumulated across *both* fingers, so a jittery second finger pushes it past `TAP_SLOP`.

## Changes

### A. Shared clipboard key (both platforms)
The companion needs the PC's `remote_secret_code`, but the user almost never types the optional permanent key during pairing. Pull it from the live connection instead of `localStorage`-only.

- **`src/companion/cloud.ts`** — when the host approves / auth-ok lands, the host already has `remote_secret_code`; add it to the `auth-ok` message broadcast (or expose via the existing `data`-channel `focus`-style unsolicited push). Minimal change: have the host include `{event:"secret", secret}` once per authorized session.
- **`src/lib/rtcHost.ts`** — on `auth-ok` send, include the secret from settings (`get_settings` already returns it to the webview via `useSettings`). Only sent to **authorized** peers (after grant) — never during negotiation, and only if the guest requested it (a flag the guest sets in its `auth` message, e.g. `wantSecret:true`). Existing trusted-device policy already gates this.
- **`src/companion/clipboardCompanion.ts`** — `init()` first tries `localStorage["gt.remote.secret"]`; if absent, it waits on the live secret push (via `getCompanionRuntime()` hook) and calls `connect()` once it arrives. Also expose a `setSecret(secret)` the runtime can call to inject it.
- **`src/companion/CompanionApp.tsx`** — on a successful `adopt()`, forward the received secret into the clip store (the deep-link-typed optional field stays as a manual override).
- **Android native service (`ClipboardService.java`)** — its push socket can't decrypt, but it doesn't need the secret for *display* (the webview does). Leave the native socket as-is; the bubble UI change (B) decrypts in Java using the secret the `startService` bridge already persists in `SharedPreferences`.

> Scope note: A is the load-bearing fix for "nothing happens when I type in the composer". Without the secret, no amount of UI change helps. If you'd rather the desktop **not** push the secret to the phone at all (privacy stance — phone must always type the permanent key manually), I'll instead change the companion to **nag clearly** ("Enter the permanent key from your PC's Remote page" with a deep link) and not auto-acquire it. Default plan is the auto-acquire path.

### B. Android native mini-panel (bubble works standalone)
`scripts/android-templates/ClipboardService.java`:

- **Tap no longer opens the app.** `DragTap.ACTION_UP` (no drag) → `showPanel()` (new), which inflates an overlay `LinearLayout` (`TYPE_APPLICATION_OVERLAY`, ~320dp wide, ~min(420, 70% screen) tall) anchored near the bubble, containing: a header ("Clipboard" + close), a scrollable list of the last ~8 items, and a footer ("Open app" secondary + "Copy last").
- **Native decrypt.** Port the crypto (`clipboardCrypto.ts` → Java): `deriveKey` (HKDF-SHA256, info=`"gt-clipboard-v1"` as salt → mirror exactly) and AES-256-GCM `iv(12)||ct||tag`. The existing push WS already carries `{t:"item", itemId, textCipher(b64), kind, …}` — store these in an in-memory `ArrayList<ClipEntry>` in the service. Images are skipped in the panel (text-only; tap "Open app" for images) to keep the bubble small and avoid image-blob fetching/decoding complexity in Java.
- **List rendering.** `ListView`/`RecyclerView` is overkill for ~8 rows; a hand-rolled `LinearLayout` of `TextView` rows (decrypted text, truncated to 2 lines; tap → `writeClipboard(text)` natively + toast "Copied") is simpler and dependency-free.
- **Keep `openApp()`** but call it only from the "Open app" footer button (still seeds `gt_open=clipboard`).
- **"Copy last"** copies the most recent decrypted text item natively (`ClipboardManager`) — no app switch.
- **Dismiss** the panel on outside-touch (`FLAG_WATCH_OUTSIDE_TOUCH` + `ACTION_OUTSIDE`) and on Close.
- The existing `showNewItemAttention()` pulse + notification stays.

Files:
- `scripts/android-templates/ClipboardService.java` (rewritten bubble logic + new `showPanel`/crypto/row rendering).
- `scripts/patch-android.mjs`: no change needed — it already copies `ClipboardService.java` verbatim and the manifest already declares the service. Add a proguard keep (already present, line 619).

### C. Desktop overlay visibility (root background)
- **`src/features/clipboard/ClipboardOverlay.tsx`** — in the mount `useEffect`, also set `document.getElementById("root").style.background = "transparent"` (and restore on unmount). This is the targeted fix that matches the existing `documentElement`/`body` clears already there.
- Guard so it only runs in the overlay route (it already only mounts at `/clip-overlay`, so this is safe — the main shell never renders this component).

No change to `index.html` (keeps the anti-flash dark for the main window) or `tauri.conf.json` (keeps `transparent:false` for the main window — only the overlay window is transparent, which it already is in `clipboard/mod.rs`).

### D. Settings → clipboard panel no longer "masked"
- **`src/features/clipboard/ClipboardSettings.tsx`** — render `<ClipboardIntro>` via a React portal to `document.body` (using `createPortal`, the existing pattern from `Modal.tsx`/`Captures.tsx`). This escapes the transformed/clipped Settings `<Panel>` so the fixed overlay actually covers the viewport and the bottom buttons are reachable.
- The rest of the rows (toggles) are fine and stay inside the panel.

### E. Two-finger right-click reliability
- **`src/companion/screens/Control.tsx`**:
  - Track `twoDownT` and `twoMaxMove` separately (new refs), set when the **second** finger lands (`pts.size === 2` in `onPointerDown`) and reset on each second-finger move.
  - In `onPointerUp`, when the gesture is `"two"` and `twoMode === "undecided"`, compute the tap test against `twoDownT`/`twoMaxMove` (not the single-finger `downT`/`maxMove`). Thresholds stay (`TAP_MS`, `TAP_SLOP`).
  - Both existing right-click sites (line 2397 touch path, line 2401 `g === "two"` path) switch to the two-finger-specific values.
- Also: bump `TAP_MS` slightly for two-finger only (e.g. 400ms) since two-finger taps are inherently slower than one-finger — keep single-finger at 260ms.

## Verification

- **Typecheck**: `npx tsc --noEmit` after the TS changes.
- **Rust**: no Rust changes (all fixable in TS/Java).
- **Manual (desktop)**: enable Shared clipboard in Settings → overlay bubble appears as a transparent rounded circle (no dark square behind it); opening the Clipboard panel from Settings shows the intro modal full-screen, buttons reachable.
- **Manual (phone)**: pair without typing a permanent key → open Clipboard tab → subtitle shows "Synced"/"Connecting…" (not the "set your key" message) and typed text appears on the PC. Tap the floating bubble → mini-panel opens over the current app, shows recent clips, "Copy last" works without switching apps.
- **Two-finger**: in Control, two-finger tap reliably fires a right-click even when fingers land ~150ms apart and jitter slightly. (Quest surface touchpad already uses `e.button === 2` — unaffected.)

## Risk / non-regression notes
- The secret push (A) only fires post-auth and only on request — does not weaken the existing per-device approval flow. If you prefer the phone **not** receive the secret automatically, say so and I'll switch A to a clear manual-entry nag instead.
- The Android mini-panel (B) is a meaningful rewrite of `ClipboardService.java`; I'll keep the WS reconnect / FGS / boot-receiver / notification logic byte-for-byte identical and only swap the bubble-tap behavior + add the panel.
- Crypto port (B) is the highest-risk piece — I'll mirror `clipboardCrypto.ts` exactly (same HKDF salt `gt-clipboard-v1`, same `iv||ct` layout) and add a tiny self-test (encrypt/decrypt round-trip) in the service `onCreate` guarded behind a debug flag so a mismatch is caught loudly, not silently.
