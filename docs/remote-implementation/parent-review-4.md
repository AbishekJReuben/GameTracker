## Developing-source findings

- **R10: restore portrait semantics after fallback recovery.** `capture_broker.rs::OutputState::poll` sets rotation to zero after an xcap/GDI fallback image, which is already oriented for the desktop. A later successful DXGI acquisition must restore the native output binding's rotation. It must also avoid presenting stale fallback data or stale sequence identity as the recovered duplication source before a valid native frame exists. Sent to the implementation agent for a fix and transition coverage; review pending.
- **R11: prevent opposite adapter lock order.** The developing `capture_surface.rs::Frame` holds its selected adapter guard while `Surface::compose` locks foreign adapters. Overlapping surfaces selected on opposite adapters can therefore acquire A then B and B then A. Capture generations can overlap while an old frame finishes, so a single current primary request does not establish mutual exclusion. Required fix: deterministic global lock order or preparation of foreign tiles without holding the selected adapter guard, with bounded concurrent regression coverage. Sent; review pending.
- **R12: composite the combined cursor after the tiles.** The developing All path paints the normal cursor into its owning output tile, including foreign-device tiles before asynchronous transfer. The tile viewport clips a shape straddling a monitor seam, and a retained foreign tile can carry a stale cursor while another output draws the new one. Required fix: cursor-free source tiles plus one final cursor pass in combined desktop coordinates for both native-GPU and CPU/JPEG delivery, retaining single-display behavior. Renderer fixtures should cover seam-straddling shapes and transfer lag without using the real pointer. Sent; review pending.
- **R13: acknowledge what is actually restored after rollback.** The developing timeout model restored an old applied identity and enabled input when that old source produced again. A client might still show a newer view whose acknowledgment was lost/failed. Required fix: remain pending until the client proves the restored frame/view is displayed, covering both input and overlay presence. The acknowledgment must distinguish this rollback transaction from a delayed/replayed acknowledgment from the old view's earlier lifetime, while retaining exact RTC peer/track binding and bounded peers. The agent agreed to the fix; final protocol and regression review are pending.
- **R14: return credits for frames retired before emission.** The developing `emit_source` rejects a retired identity after callers have evaluated `permit.packet(pkt)`. That consumes the delivery permit with `sent=true`, even though no packet is emitted and no host acknowledgment can return its credit. Two such drops can fill the native delivery window until its two-second timeout disables fast delivery. Required fix: keep the permit unsent until source validation succeeds, or explicitly return rejected credits. A received stale packet must also be acknowledged before host identity-based discard. Sent for a supersession/drop regression and source fix; review pending.
- **R15: track the injected key/button identity.** The developing held-input maps use raw names while injection normalizes aliases/defaults, so `ctrl`, `control`, and `CTRL` can create different entries for one OS key. Invalid multi-character names also returned success and were stored. Required fix: canonical validated identities, correct alias/case release and two-session ownership, removal of empty entries, and defined behavior when a one-shot Click implicitly releases an already-held key/button. A second session must not silently invalidate another session's drag/hold. Sent for source and regression coverage; review pending.
- **R16: bind recovery to the emitted source.** The readback encoder's in-flight old `RawFrame` can consume a global `NATIVE_FORCE_KEY` set for the next source, encode an old IDR that is then retired, and leave the following equal-sized new-epoch frame as a P-frame on the retained encoder. Required fix: recover/rebuild based on the last successfully emitted source identity, so every new/rollback epoch starts with an independently decodable emitted frame on the CPU/native fallback as well as zero-copy. Sent for an in-flight retired-frame/same-size transition regression; review pending.
- **R17: reconcile the RTC commit notification.** The developing epoch-video host retires the old peer after native acknowledgment, then ignores a failed `epoch-video-committed` send. The client remains pending and can time out/retire the new peer while the host believes it is active and native state is applied. Required fix: explicit retry/confirmation or authoritative status reconciliation for commit notification failure/loss, preserving the two-peer bound and working without an unrelated reconnect. Also test same-view watchdog track replacement: the initial module's stage method no-ops for an already active identity. Sent for module/integration coverage; review pending.
- **R18: do not relabel a preceding view's reliable pointer anchor.** The developing `makeRtcLink` stores `lastAbsolute` without its producing/applied epoch, then wraps it with whatever epoch is current when the next click/down/up is sent. A toolbar click after a Focus, single-display or topology transition can therefore reposition using coordinates from the preceding view. Required fix: bind or invalidate saved anchors at view/session changes and preserve correct button-release delivery. Cover the first button action after an equal-size switch without an intervening pointer move, as well as a move refused during a pending change. Sent for source and regression coverage; review pending.
- **R19: preserve gamepad neutralization during a pending view.** The developing client deliberately allows `gamepadstop` through its pending-view release gate, but the native `Controller::releases_only` accepts only mouse up, key up and nested sequences. An epoch-wrapped stop therefore disappears when input is blocked, allowing the preceding XInput state to remain held. Required fix: preserve the existing neutralize/unplug operation through pending/stale-view release handling, with a regression of the actual release dispatch and teardown path. Sent; review pending.
- **R20: reject a stale topology status as a whole.** Parent's independent seven-case coordinator probe reproduces a failure: after a valid pending epoch 2 / layout 2 status and its actual presented frame, a delayed epoch 1 / layout 1 status is rejected by `DisplayedView.observe` but still overwrites `ClientViewSession.layout`. The following epoch 2 confirmation is paired with layout 1, affecting presence/monitor controls until another poll. Required fix: adopt topology only with an accepted matching requested identity and validate the full snapshot; never regress the known topology after rejecting an old/conflicting view. Six other independent coordinator scenarios pass. Sent with the runnable fixture; review pending.
- **R21: separate native transition retention from final teardown and bound pending copies.** The developing native wrapper calls `prepareTransition` before every init and teardown, including final disconnect/unmount/reset cleanup. A failed picture copy must not prevent final codec teardown; a successful copy must not recreate an orphan retained ImageView after `close` already cleared it. Use explicit transition-versus-final lifecycle intent and invalidate stale queued work before allocating. The pending PixelCopy path must have a single-flight/allocation bound even if UI/copy callbacks outlive the 450 ms caller timeout. Also verify the native-to-RTC/WebCodecs handoff keeps its old picture visible: the ImageView is below WebView, while `wcNative=false` restores opaque DOM ancestors and closes the transparency punch before the new visible element's frame boundary. Required source/lifecycle/retention evidence is pending; one-decoder ownership must remain.
- **R22: do not lose keyboard/text or gamepad releases during a view change.** The developing `sendViewInput` and native blocked-view path reject all non-release events, although the plan's transition gate targets coordinate-dependent presses and keeps keyboard input on the real foreground application. Control's existing direct-IME `flushDiff` advances `prevVal` after a refused text/backspace send, so text entered during a switch is silently forgotten. Full gamepad reports containing released buttons can likewise be dropped, retaining the previous state. Preserve authorized non-coordinate input during pending view changes, or retain/replay it with explicit correctness and bounds. Superseded/unauthorized sessions must remain blocked, coordinate-containing sequences must remain atomic, and necessary releases must remain available. Cover real client/native dispatch classification plus the IME boundary. Sent; review pending.

R17 integration follow-through: a failed same-identity watchdog peer must also retire/reset its exact pending `CaptureVideoFeed`. Initially that pending track remained after the peer was retired: `ensureTrack` did not call its ready callback again, `rebuild` refused while any pending feed existed, and native cancel was a no-op for an already-applied identity. Require a bounded retry after a failed first rebuild offer/setup, retaining active/newer sources. This is outside the successful standalone peer-module probe below.

The approved active-peer gate also applies on RTC-to-DIRECT/carrier changes. A different-identity DIRECT commit may retire the active epoch peer; the developing host's separate `activeVideoPc`/sender references must then be updated so stats, bitrate and watchdog work do not continue using a closed peer. Verify a subsequent return to RTC and cancellation of any pending video peer.

R19 cleanup must distinguish inactive Control/PiP/immersive scope from an active viewport whose visible-display intersection is empty. Panning a combined view into a physical gap should hide its decoration without implicitly releasing an existing drag. Explicit inactivity, expiry and retirement must still release owned input.

Retained H integration risks from the existing paths:

- The Android bridge's current `frames` counter advances after `releaseOutputBuffer(..., true)`, before a rendered-surface callback. - Topology refresh and capture-generation overlap must not place new-layout pixels into an old RTC track or mislabel a queued encoder result. A requested layout alone is not evidence of the producing source.
